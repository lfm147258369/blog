# 第二章操作系统接口

## 从启动到 system：操作系统的存在感

### 操作系统的整体轮廓


* system：操作系统最终运行起来的整体
* 手写关键词：

  * IDT（中断描述符表）
  * GDT（全局描述符表）
  * mem_map（内存页映射）
  * OS（操作系统）
* 数字“0”：暗示从最底层（地址 0）开始
* 红色箭头：表示**启动流程是逐步推进的**

这一页的核心目的只有一个：

> 操作系统不是“凭空出现的程序”，而是从最底层一步步建立起来的系统。

## 什么是接口（Interface）

### 从生活常识理解接口

* 日常接口的例子：

  * 电源插座
  * 汽车油门踏板
* 接口的作用：

  * 连接两个东西
  * 做信号转换
  * 屏蔽内部细节

> 牛津词典定义（核心含义）：
> Interface 是一种连接机制，使一种格式的数据可以被另一种系统理解和使用。

## 什么是“操作系统接口”

### 操作系统接口初步直觉

表面现象：

* 输入命令 `hello`
* 屏幕显示 `hello`
* 看起来像是：

  ```
  用户 → 操作系统 → 屏幕
  ```

但问题马上出现：

* 操作系统**真的直接面对用户吗？**
* 用户是“怎么”使用操作系统的？

## 从提问开始理解：用户真的在用操作系统吗？

### 用户如何使用计算机

真实结构是分层的：

* 应用软件
* 操作系统
* 计算机硬件

用户看到的三种常见形式：

* 命令行

  ```
  ./output "hello"
  → ECHO:hello
  ```
* 图形按钮
  点击桌面图标、菜单项
* 应用程序
  Word 文档、浏览器、工具软件

结论先放出来：

> 用户**不直接**和操作系统交互
> 用户是在使用**应用程序**

## 命令行到底是什么

### 命令的本质

一个“命令”本质上就是一个程序：

```c
#include <stdio.h>
int main(int argc, char * argv[])
{
    printf("ECHO:%s\n", argv[1]);
}
```

* 编译：`gcc -o output output.c`
* 执行：`./output "hello"`

所以：

> 命令 ≈ 一个可执行程序

---

### shell 又是什么

shell 本身也是程序（如 `/bin/sh`）：

```c
int main(int argc, char * argv[])
{
    char cmd[20];
    while(1) {
        scanf("%s", cmd);
        if(!fork()) { exec(cmd); }
        else { wait(); }
    }
}
```

关键点：

* shell 负责：

  * 读命令
  * 创建进程
  * 执行程序
* shell **不是操作系统**
* shell 是运行在操作系统上的应用程序

## 图形界面是怎么工作的

### 图形按钮的真实流程

当你点击一个按钮：

* 硬件产生输入
* 操作系统放入系统消息队列
* 应用程序从消息队列取消息
* 应用程序处理消息

典型结构：

* `WinMain()`：消息循环（`GetMessage`）
* `WinProc()`：消息处理函数
* 示例：

  ```c
  case WM_MOUSEDOWN:
      OnOK();
  ```

而 `OnOK()` 只是普通 C 代码：

```c
void COutputDlg::OnOK()
{
    GetDlgItemText(IDC_EDIT1, m_outStr);
    FILE *fp = fopen("d:\\out.txt", "w");
    fprintf(fp, m_outStr, m_outStr.GetLength());
    fclose(fp);
}
```

结论非常重要：

> 图形界面 ≈ 一个“会画界面 + 处理消息”的 C 程序

## 再回到核心问题：什么是操作系统接口

### 用户、应用、操作系统的真实关系

* 用户 → 应用程序
* 应用程序 → 操作系统
* 操作系统 → 硬件

连接应用程序与操作系统的，不是按钮，也不是命令本身，而是：

> **函数调用**

---

### 操作系统接口的本质

* 表现形式：函数
* 使用方式：C 语言调用
* 提供者：操作系统

例如：

```c
fork();
open();
```

这些函数：

* 看起来是普通函数
* 实际由操作系统完成
* 应用程序无法自己实现

所以它们有一个专门的名字：

> **系统调用（System Call）**

---

## 用一个概念回答：什么是操作系统接口

### 操作系统接口 = 系统调用

类比：

* 电器 ← 插头 → 电源
* 应用程序 ← 系统调用 → 操作系统

---

### POSIX：操作系统接口的标准

* POSIX = Portable Operating System Interface of Unix
* 由 IEEE 制定
* 定义了：

  * 系统调用
  * 数据结构
  * 错误码

示例（理解层面即可）：

* 进程管理：`fork`
* 文件系统：`open`
* 错误返回：`EACCES`
* 文件属性：`mode_t st_mode`

这说明：

> 操作系统接口不是“随便设计的”
> 而是有标准、有规范的

---

### 小结

* 用户不直接使用操作系统
* 用户通过**应用程序**使用计算机
* 应用程序通过**系统调用**使用操作系统
* 操作系统接口的本质：
  **系统提供的一组函数调用**

## 内核态 / 用户态，与内核段 / 用户段

核心目标：**将内核程序和用户程序彻底隔离**

---

一、为什么要区分“内核态”和“用户态”

根本目的只有一个：

> **防止用户程序破坏操作系统本身**

需要解决的问题

* 用户程序不能随意访问内核数据
* 用户程序不能随意执行特权指令
* 用户程序只能“请求”操作系统服务，而不是“控制”操作系统

为此，引入一种**处理器级别的硬件设计**：特权级。

---

二、处理器的特权级设计（保护环模型）

处理器内部定义了多个执行级别（同心圆）：

```
Ring 3：用户态（最低特权）
Ring 2：中间层（很少使用）
Ring 1：中间层（很少使用）
Ring 0：内核态 / 核心态（最高特权）
```

要点

* 当前程序**一定运行在某一个特权级**
* 特权级由**硬件强制执行**，不是操作系统“自觉遵守”

---

三、当前程序“在哪一层”，硬件如何判断？

关键寄存器

* `CS:IP` 指向当前正在执行的指令
* **CS 寄存器的最低两位**表示当前特权级（CPL）

对应关系

* `CPL = 0` → 内核态（Ring 0）
* `CPL = 3` → 用户态（Ring 3）

这意味着

* 只要代码在执行，CPU 就**实时知道**它是内核代码还是用户代码
* 权限判断是“每条指令级别”的，而不是程序级别的

---

四、内核段 / 用户段：权限不是“代码决定”，而是“段决定”

在保护模式下：

* 段寄存器不再是地址
* 段描述符中包含**特权级属性（DPL）**

于是出现了两类段

* 内核代码段 / 内核数据段（DPL = 0）
* 用户代码段 / 用户数据段（DPL = 3）

代码能不能访问某个数据段，**不是看“你想不想”，而是看“能不能通过硬件检查”**。

---

五、访问数据段时的三重特权级检查（重点）

当代码访问一个数据段时，CPU 会同时检查三个特权级：

| 名称  | 含义                     |
| --- | ---------------------- |
| CPL | 当前代码段的特权级（CS 的最低两位）    |
| RPL | 数据段选择子的请求特权级（DS 的最低两位） |
| DPL | 目标数据段描述符的特权级           |

硬件必须满足的条件（两条同时成立）

* `DPL ≥ CPL`
* `DPL ≥ RPL`

只要有一条不满足
→ **硬件直接拒绝访问（异常）**

---

补充说明：CS / DS 到底是什么？

在保护模式下，**CS 和 DS 都不再是“地址”本身**，而是：

> **段选择子（selector）**

它们的作用是：
→ 指向 GDT / LDT 中的某一个段描述符。

---

一、CS（Code Segment，代码段寄存器）

CS 的含义可以记成一句话：

> **CS 指向“当前正在执行的代码段”**

作用

* 决定 CPU **从哪个段取指令**
* 决定当前程序的**执行特权级**

关键点

* CS 的**最低两位**表示当前特权级
* 这两位被称为 **CPL（Current Privilege Level）**

也就是说：

```
CPL = CS & 0b11
```

例子

* CS 低两位 = `00` → 内核态（Ring 0）
* CS 低两位 = `11` → 用户态（Ring 3）

所以可以这样记：

> **CPL 不是一个独立寄存器，它是 CS 的一部分**

---

二、DS（Data Segment，数据段寄存器）

DS 的含义同样一句话就够：

> **DS 指向“当前默认使用的数据段”**

作用

* 决定普通内存访问（如变量、数组）**使用哪个段**
* 是用户程序和内核程序访问数据时最常用的段寄存器

关键点

* DS 里存放的也是一个**段选择子**
* DS 的**最低两位**称为 **RPL（Request Privilege Level）**

也就是说：

```
RPL = DS & 0b11
```

RPL 的含义

* 表示：**“我请求以什么特权级来访问这个段”**
* 是一种“自我限制”机制
* 即使当前在高特权级，也可以用低 RPL 去访问数据

---

三、DPL：段“自身”的特权级

DPL 不在 CS 或 DS 里，而在：

> **段描述符中**

含义

* 表示：**这个段允许被什么级别的程序访问**
* 是段的“固有权限”

常见情况

* 内核数据段：`DPL = 0`
* 用户数据段：`DPL = 3`

---

四、三者关系汇总（专为复习准备）

| 名称  | 来自哪里     | 表示什么          |
| --- | -------- | ------------- |
| CPL | CS 的最低两位 | 当前代码正在运行的特权级  |
| RPL | DS 的最低两位 | 访问数据时“请求”的特权级 |
| DPL | 段描述符     | 该段本身允许的访问特权级  |

硬件检查的本质可以理解为一句话：

> **你现在是谁（CPL），你想以什么身份访问（RPL），以及这个段允不允许你这么做（DPL）**

---

五、为什么这一步对“系统调用”至关重要

因为接下来你会看到：

* 用户态代码（CPL=3）
* 却能“合法地”进入内核态（CPL=0）
* **而不违反任何特权级规则**

那一定意味着：

> **系统调用不是普通的跳转，而是硬件支持的特权级切换机制**



---

六、这套机制带来的直接效果

结果不是“约定”，而是**物理隔离**：

* 用户态代码

  * 不能访问内核数据段
  * 不能加载内核段到段寄存器
  * 不能执行特权指令

* 内核态代码

  * 可以访问所有段
  * 可以执行特权指令
  * 可以管理系统资源

---

七、与前一节“whoami 问题”的直接衔接

前一页的问题是：

> 用户程序能不能直接访问内核中的字符串？

在这里得到答案：

* **不能**
* 因为用户程序运行在用户态（CPL=3）
* 内核数据段的 DPL=0
* 特权级检查无法通过

因此结论自然推出：

> **用户程序想使用内核功能，只能通过一种“受控的、合法的特权级切换方式”**

这正是下一步要讲的内容：

* 系统调用
* 从用户态进入内核态的唯一合法入口

---


## 硬件提供了“主动进入内核的方法”


> **用户程序在用户态，凭什么、又是怎么合法进入内核态的？**

答案不是“jmp”，而是：**硬件提供了受控入口**。

---

### 一、为什么必须由硬件提供入口

前一节已经明确：

* 用户态（CPL = 3）
* 内核态（CPL = 0）
* 普通跳转 **不能跨特权级**

如果允许用户程序随意：

* 跳转到内核代码
* 访问内核数据

那么结果就是：

* 能读 root 密码
* 能改内核数据
* 整个系统失去隔离

所以结论是：

> **“进入内核”这件事，必须由 CPU 硬件亲自控制**

---

### 二、x86 体系下的解决方案：`int` 指令

在 Intel x86 架构中，硬件给出的方案是：

> **中断指令 `int`**

关键特性：

* `int n` 是一条**特权级切换指令**
* 执行后：

  * CPU **自动将 CPL 从 3 切换为 0**
  * 跳转到内核中对应的中断处理代码
* 用户程序**不能伪造这个过程**

总结:

> **`int` 是用户程序“合法请求内核服务”的唯一硬件通道**

---

### 三、这里为什么“CPL = 3，而 DPL = 0”仍然能进内核


直观理解：

* 用户程序当前：

  * CPL = 3（在用户态）
* 内核代码段：

  * DPL = 0（只允许内核态执行）

按普通规则：
CPL > DPL → 不允许访问

但 `int` 是**特殊指令**：

> **`int` 不走普通段访问规则，而是走“中断门”规则**

也就是说：

* 是否允许进入内核
* 不由 CS/DS 的比较决定
* 而由 **IDT 中中断门的 DPL 决定**

这是硬件“开后门”，但这个后门：

* 只能由操作系统提前设置
* 用户无法绕过或伪造

---

### 四、系统调用在逻辑上的三步流程

“由谁做？库函数！”，这是重点。

可以整理成一条非常清晰的调用链：

1. 用户程序

   * 调用一个**看起来是普通函数**的接口
   * 例如：`open()`、`read()`、`fork()`

2. C 库函数（如 glibc）

   * 在函数内部执行：

     * 设置系统调用号
     * 执行一条 `int` 指令

3. 操作系统内核

   * 中断处理程序：

     * 读取系统调用号
     * 分发到对应的内核函数
     * 执行真正的内核逻辑

一句话总结：

> **用户“调用函数”，库函数“发中断”，内核“干活”**

---

### 五、这一节在整章里的地位

到这里为止，已经回答了三个问题：

1. 为什么要区分用户态 / 内核态
2. 为什么用户不能直接调用内核代码
3. 用户是**如何合法进入内核的**




## 系统调用的实现：从“为什么需要”到“如何做到”

---


### 特权级概念补充（防止复习时遗忘）

| 名称      | 含义                     |
| ------- | ---------------------- |
| **CPL** | 当前代码段的特权级（CS 的最低两位）    |
| **RPL** | 段选择子的请求特权级（如 DS 的最低两位） |
| **DPL** | 目标段描述符中规定的特权级          |

**典型场景：**

* 用户态：`CPL = 3`
* 内核态：`CPL = 0`
* 执行 `int` 时，由硬件完成特权级切换，而不是程序自己改

---

### 系统调用的核心流程

**系统调用本质只有三步：**

1. **用户程序中执行一段包含 `int` 指令的代码**
2. **操作系统编写中断处理程序**

   * 读取系统调用编号
3. **内核根据编号，分发并执行对应的内核函数**

> 用户程序并不知道内核函数地址
> 只知道：“我要第 N 号服务”

---

### 真实世界里的调用链（以 `printf` 为例）

#### 调用流程（逻辑视角）

```
应用程序
  ↓
C函数库 printf(...)
  ↓
C函数库 write(...)
  ↓
OS内核 write 系统调用
```

**要点：**

* 用户程序**并不直接写 `int`**
* `int` 被**封装在 C 库函数里**

---

### 七、代码层面的对应关系

#### C库中的系统调用封装

**`linux/lib/write.c`：**

```c
#include <unistd.h>
_syscall3(int, write, int, fd, const char *buf, off_t, count)
```

#### 宏展开后的本质

**`linux/include/unistd.h` 中：**

```c
#define _syscall3(type, name, ...) \
type name(...) { \
    __asm__("int 0x80" : "=a" (__res) ... ); \
}
```

**关键信息：**

* 最终一定会展开成：

  * 一段 **包含 `int 0x80` 的汇编代码**
* 这正是：

  * 用户态 → 内核态
  * 的唯一合法跳板

---

### 小结（这一页的核心结论）

* 系统调用不是“普通函数调用”
* 用户程序 **不能直接执行内核代码**
* 硬件提供：

  * `int` 指令
  * 强制特权级切换
* C库的作用：

  * **替用户封装 `int`**
  * 提供“看起来像函数”的系统调用接口

## write 



### 一、从 C 库里的 write 说起

用户程序中调用的 `write`，并不是内核函数，而是 **C 函数库提供的封装**。

这一层的目标只有一个：

> 把“函数调用”翻译成一次 **`int 0x80` 系统调用**

---

### 二、_syscall3 宏展开后到底做了什么？

* 代码片段（`linux/include/unistd.h`）

```c
#define _syscall3(type,name,atype,a,btype,b,ctype,c) \
type name(atype a, btype b, ctype c) \
{   long __res; \
    __asm__ volatile( \
        "int 0x80" \
        : "=a" (__res) \
        : "a" (__NR_##name), \
          "b" ((long)(a)), \
          "c" ((long)(b)), \
          "d" ((long)(c)) \
    ); \
    if (__res >= 0) return (type)__res; \
    errno = -__res; \
    return -1; \
}
```


#### 二、_syscall3 宏展开后到底做了什么（逐行拆解）

这段宏代码的**目标只有一个**：

> 把一次普通的 C 函数调用
> 变成一次符合内核约定的 `int 0x80` 系统调用

---

 1. 宏的整体展开结果是什么？

```c
type name(atype a, btype b, ctype c)
```

这说明：

* `_syscall3` **最终生成的是一个普通的 C 函数**
* 函数名就是 `name`（例如 `write`）
* 参数个数是 3 个（这也是 `_syscall3` 的含义）

所以在用户代码里：

```c
write(fd, buf, count);
```

**调用的其实是这个宏生成的函数**

---

 2. `__res` 是什么？

```c
long __res;
```

* `__res` 用来保存：

  * **系统调用的返回值**
* 为什么用 `long`：

  * 系统调用返回值来自寄存器 `eax`
  * `eax` 在 32 位下就是一个整型寄存器

---

 3. asm volatile 是什么角色？

```c
__asm__ volatile( ... );
```

含义拆开来看：

* `__asm__`：直接写汇编
* `volatile`：告诉编译器

  * 这段汇编**不能被优化、不能被删、不能重排**

原因很关键：

> `int 0x80` 有副作用
> 会改变 CPU 特权级、寄存器、控制流

---

 4. `"int 0x80"` 到底做了什么？

```c
"int 0x80"
```

这一条指令完成三件事：

1. 触发 **0x80 号中断**
2. CPU 自动：

   * 保存现场
   * 将 CPL 从 3 切换到 0
3. 跳转到内核的系统调用入口

**这是用户态进入内核态的唯一合法通道**

---

 5. 输出约束：`"=a" (__res)`

```c
: "=a" (__res)
```

这是 **汇编的输出部分**，含义是：

* `"=a"`：

  * 输出来自 `eax` 寄存器
* `(__res)`：

  * 把 `eax` 的值保存到变量 `__res`

也就是说：

> **系统调用返回值 = eax → __res**

---

 6. 输入约束：系统调用号和参数怎么传？

```c
: "a" (__NR_##name),
  "b" ((long)(a)),
  "c" ((long)(b)),
  "d" ((long)(c))
```

这是 **汇编的输入部分**，一条一条看。

---

 6.1 系统调用号

```c
"a" (__NR_##name)
```

* `"a"`：使用 `eax` 寄存器
* `__NR_##name`：

  * 对 `write` 来说就是 `__NR_write`

含义：

> `eax = 系统调用号`

---

 6.2 第一个参数

```c
"b" ((long)(a))
```

* `"b"`：使用 `ebx`
* `(a)`：函数第一个参数

含义：

> `ebx = 第 1 个参数`

---

 6.3 第二、第三个参数

```c
"c" ((long)(b))
"d" ((long)(c))
```

对应：

| 参数      | 寄存器 |
| ------- | --- |
| 第 2 个参数 | ecx |
| 第 3 个参数 | edx |

---

 6.4 为什么一定是这几个寄存器？

这是 **Linux x86 的系统调用 ABI 约定**：

* 内核和用户态 **事先约定好**
* 内核入口代码只从这些寄存器取参数

用户程序 **不能随便选**

---

 7. int 返回后，C 代码怎么处理结果？

```c
if (__res >= 0)
    return (type)__res;
```

* 返回值 ≥ 0：

  * 系统调用成功
  * 直接返回给用户程序

---

```c
errno = -__res;
return -1;
```

* 返回值 < 0：

  * 内核用负值表示错误码
  * C 库负责：

    * 设置 `errno`
    * 返回 -1（符合 POSIX 约定）

---

 8. 总结这段宏在干什么

**这段代码本质就是：**

1. 把系统调用号放入 `eax`
2. 把参数放入 `ebx / ecx / edx`
3. 执行 `int 0x80`
4. 从 `eax` 取回返回值
5. 转换成 C 语言习惯的返回方式

---

 9. 图示一下整个过程

以后看到 `_syscall3`，直接替换成：

```
准备寄存器
→ int 0x80
→ eax 取返回值
```


---

### 三、这里发生的关键事情

**1 系统调用号的传递**

* `__NR_##name`
* 对 `write` 而言，就是 `__NR_write`
* 被放入 **`eax` 寄存器**

> `eax` = 我要调用哪个 系统调用

---

**2 参数的传递方式（由 ABI 规定）**

| 寄存器   | 含义      |
| ----- | ------- |
| `eax` | 系统调用号   |
| `ebx` | 第 1 个参数 |
| `ecx` | 第 2 个参数 |
| `edx` | 第 3 个参数 |

对应 `write(fd, buf, count)`：

* `ebx ← fd`
* `ecx ← buf`
* `edx ← count`

---

**3 执行 int 0x80**

* `int 0x80` 触发中断
* CPU：

  * 切换到内核态（CPL=0）
  * 跳转到系统调用中断处理入口
* 用户程序 **无法控制跳转位置**

---

### 四、系统调用号从哪里来？

* 代码片段（`linux/include/unistd.h`）

```c
#define __NR_write 4
```

**含义：**

* 系统调用号是一组 **连续的正整数**
* 本质上是：

  * 系统调用表（函数指针数组）的 **索引**

> `__NR_write = 4`
> ⇒ 内核中 `sys_call_table[4] = sys_write`

---

### 五、返回值是怎么回来的？

* 内核执行 `sys_write`
* 返回值放入 **`eax`**
* `int` 返回后：

  * `eax` 回到用户态
  * 被保存到 `__res`

处理逻辑：

* `__res >= 0`：成功，返回结果
* `__res < 0`：失败，设置 `errno`

---

### 六、这一节逻辑梳理

**至此，write 的整条路径是闭合的：**

1. 用户程序调用 `write(...)`
2. C 库：

   * 把参数放入寄存器
   * 把系统调用号放入 `eax`
3. 执行 `int 0x80`
4. 内核：

   * 根据 `eax` 查系统调用表
   * 执行 `sys_write`
5. 返回值通过 `eax` 回到用户态

---

### 七、结论

* `write` **不是普通函数**
* `_syscall3` 的本质：

  * **寄存器赋值 + int 指令**
* 系统调用：

  * 参数靠寄存器传
  * 系统调用号是数组下标
  * 返回值仍然走 `eax`

---




## int 0x80 中断的处理

---

### 一、主干逻辑总览（这一页在讲什么）

这一页回答的是一个核心问题：

> **当用户态执行 `int 0x80` 时，CPU 是怎么知道该跳到哪段内核代码的？**

答案是三步：

1. **内核提前初始化 IDT 的第 0x80 项**
2. **把 system_call 的地址写进中断门描述符**
3. **CPU 执行 `int 0x80` 时，根据 IDT[0x80] 自动跳转**

---

### 二、0x80 中断门是在什么时候、由谁设置的？

* 1. 中断门初始化代码（主干）

```c
void sched_init(void)
{
    set_system_gate(0x80, &system_call);
}
```

* 主干说明

* `sched_init()` 是内核初始化阶段调用的函数
* 这里明确做了一件事：

  * **把 0x80 号中断，绑定到 system_call 这个内核函数**

一句话概括：

> **内核在启动时就规定好了：int 0x80 → system_call**

---

* 细节点补充：为什么是 sched_init？

* Linux 0.11 中，`sched_init` 不只是调度初始化
* 它顺带完成：

  * 中断相关
  * 系统调用入口的初始化
* 这属于早期 Linux “功能集中式初始化”的典型风格

---

### 三、set_system_gate 到底干了什么？

* 2. 宏定义（原代码完整保留）

```c
#define set_system_gate(n, addr) \
    _set_gate(&idt[n], 15, 3, addr); // idt是中断向量表基址
```

* 主干说明

* `idt[n]`：

  * 第 n 个中断描述符
* `15`：

  * 表示 **中断门类型**
* `3`：

  * **DPL = 3**
  * 允许用户态触发（这是系统调用的关键）
* `addr`：

  * 中断处理函数地址（这里是 `system_call`）

总结：

> **set_system_gate = 在 IDT[n] 里填一个“用户可调用的中断门”**

---

**细节点补充：为什么 DPL 一定是 3？**

* 如果 DPL < 3：

  * 用户态执行 `int 0x80` 会直接触发异常
* 系统调用的本质要求：

  * **用户态必须“被允许”进入内核**
* 所以：

  * `int 0x80` 是一个**被刻意放开的入口**

---

### 四、真正写 IDT 的底层实现

`_set_gate` 宏

```c
#define _set_gate(gate_addr, type, dpl, addr) \
__asm__( \
    "movw %%dx,%%ax\n\t" \
    "movw %0,%%dx\n\t" \
    "movl %%eax,%1\n\t" \
    "movl %%edx,%2" \
    : \
    : "i" ((short)(0x8000 + (dpl<<13) + (type<<8))), \
      "o" (*((char *)(gate_addr))), \
      "o" (*(4 + (char *)(gate_addr))), \
      "d" ((char *)(addr)), \
      "a" (0x00080000) \
)
```

* 主干说明（不拆指令）

这段汇编代码的**唯一目的**是：

> **按照 x86 中断门格式，把 system_call 的地址和属性写入 IDT 表项**

不需要在这一页完全读懂汇编，只要抓住三个结果：

1. 写入了 **处理函数入口地址**
2. 写入了 **段选择子**
3. 写入了 **类型 + DPL + P 位**






* 细节点补充（对应中断门结构）

* `0x8000`：

  * P 位 = 1（表示该门存在）
* `(dpl << 13)`：

  * 设置 DPL
* `(type << 8)`：

  * 设置门类型（中断门）

>>>
* 补充：IDT 是什么？为什么一定要用它？

**IDT（Interrupt Descriptor Table，中断描述符表）**
是 **CPU 内部使用的一张表**，专门用来回答一个问题：

> **“当发生某个中断 / 异常 / 系统调用时，CPU 应该跳到哪段内核代码去执行？”**

---

 1. IDT 在整个体系中的位置

前面学过几件事，其实已经在为 IDT 铺垫了：

* **用户态不能直接跳到内核态**

  * 不能 `jmp` / `call` 到内核代码
* **特权级切换必须由 CPU 主动完成**

  * 需要硬件机制保证安全
* **系统调用是“受控的进入内核”**

  * 不能随便进，只能走规定入口

 **IDT 就是这个“规定入口”的目录**

---

 2. IDT 解决的核心问题

当 CPU 执行到：

```asm
int 0x80
```

CPU 并不知道：

* 要跳到哪个函数
* 用什么代码段
* 是否允许 CPL=3 触发
* 是否需要切换到内核栈

于是 CPU 做一件事：

> **用中断号（如 0x80）作为索引，去 IDT 里查一项**

这一项里**已经提前写好**：

* 内核处理函数地址（如 `system_call`）
* 段选择子（内核代码段）
* DPL（是否允许用户态触发）
* 类型（中断门 / 陷阱门）
* P 位（是否有效）

---

 3. `_set_gate` 在干什么（一句话版）

你现在看到的 `_set_gate` 宏，本质上只做一件事：

> **把“中断号 → 内核入口”的规则，写进 IDT**

也就是说：

* 之前：CPU 不知道 `int 0x80` 该去哪
* 执行 `_set_gate` 之后：
  `int 0x80` → 查 IDT → 跳到 `system_call`

>>>

---

 4. 为什么这是“必须的硬件步骤”

没有 IDT：

* 用户态 **永远进不了内核**
* 或者只能用不安全的 `jmp`
* 系统调用、异常、中断全部失效

所以可以记一句话：

> **IDT 是用户态 → 内核态的“唯一合法大门”**

---

 5. 衔接

你已经学过的流程，其实是：

```
_set_gate 写好 IDT
        ↓
用户态执行 int 0x80
        ↓
CPU 查 IDT[0x80]
        ↓
跳到 system_call（CPL=0）
        ↓
sys_call_table
```

现在 `_set_gate` 这一页，正好是在补 **“这扇门是怎么被装上的”**。




---

### 五、中断门描述符结构（与代码对应）

 4. 中断门的硬件格式（主干）

```
┌────────────────────────────────┬──────────────────┐
│ 处理函数入口点偏移（高16位）   │ P DPL  01110    │
├────────────────────────────────┼──────────────────┤
│ 段选择符                      │ 处理函数入口点偏移（低16位） │
└────────────────────────────────┴──────────────────┘
```

#### 主干说明

* **偏移地址**：

  * 指向 `system_call`
* **段选择符**：

  * 内核代码段（CS）
* **P 位**：

  * 表示该中断门有效
* **DPL = 3**：

  * 允许 CPL=3 的程序触发
* **01110**：

  * 表示“中断门”

---

### 细节点补充：CPU 执行 int 0x80 时发生了什么？

当用户态执行：

```asm
int 0x80
```

CPU 自动完成：

1. 根据 0x80 查 IDT[0x80]
2. 检查：

   * CPL ≤ DPL（通过）
3. 切换：

   * CPL: 3 → 0
4. 跳转到：

   * `system_call` 的地址

**没有一行 C 代码参与这个过程，全是硬件完成**

---

### 梳理

把这一节和前面的 `_syscall3` 连起来：

```
用户程序
→ libc 中的 write()
→ int 0x80
→ CPU 查 IDT[0x80]
→ system_call（内核）
```

到这里为止，已经完整走通了：

> **“一个 C 函数调用是如何被 CPU 硬件送进内核的”**




## 中断处理程序：`system_call`

---

### 一、这一节的核心问题（主线）

这一页回答的是：

> **CPU 已经通过 `int 0x80` 进入内核了，那么：
> 内核如何根据系统调用号，找到并执行对应的系统调用函数？
> 执行完后，又如何安全返回用户态？**

---

### 二、代码位置与角色

* 文件位置：`linux/kernel/system_call.s`
* `system_call` 的角色：

  * **所有系统调用的统一入口**
  * 相当于一个“系统调用总调度器”

---

### 三、汇编代码（主线相关部分）

```asm
nr_system_calls=72
.globl _system_call

_system_call:
    cmpl $nr_system_calls-1,%eax
    ja bad_sys_call
```

* 主线解析 1：系统调用号合法性检查

* `eax`：系统调用号（这是前面 `_syscall3` 约定好的）
* 含义：

  * 如果 `eax >= nr_system_calls`，说明非法
  * 跳转到 `bad_sys_call`

**这一段的本质：**

> **防止用户随便传一个编号就执行内核任意地址**

---

```asm
    push %ds
    push %es
    push %fs
    pushl %edx
    pushl %ecx
    pushl %ebx
```

* 主线解析 2：保存现场（用户态上下文）

* 保存内容包括：

  * 段寄存器（`ds / es / fs`）
  * 参数寄存器（`ebx / ecx / edx`）

**这里不纠结顺序，只记住一句话：**

> **系统调用要像“函数调用”一样，先保存现场**

---

```asm
    movl $0x10,%edx
    mov %dx,%ds
    mov %dx,%es
```

* 主线解析 3：切换到内核数据段

* `0x10`：

  * 内核数据段选择子
* 作用：

  * 保证后续内核代码访问的是**内核的数据空间**

结论：

> **进入内核态 ≠ 已经在用内核段
> 必须显式切换 DS / ES**

---

```asm
    movl $0x17,%edx
    mov %dx,%fs
```

* 主线解析 4：fs 指向用户数据段

* `0x17`：

  * 用户数据段选择子
* 作用：

  * 内核仍然可以通过 `fs` 访问用户传进来的数据

一句话总结：

> **ds/es → 内核数据
> fs → 用户数据**

这是 Linux 0.11 一个非常经典的设计点。

---

```asm
    call sys_call_table(,%eax,4)
```

* 主线解析 5：系统调用分发表（最关键的一句）


* `eax`：系统调用号
* 每个函数指针占 4 字节
* 地址计算方式：

```
sys_call_table + 4 * eax
```

等价于 C 里的：

```c
sys_call_table[eax]()
```

**这一步完成了什么？**

> **根据系统调用号，调用对应的内核函数
> 例如：write / fork / open**

---

```asm
    pushl %eax
```

* 主线解析 6：保存返回值

* 系统调用函数的返回值在 `eax`
* 压栈的目的：

  * 为后面的 `ret_from_sys_call` 使用

**你只需要记住：**

> **系统调用的返回值最终也通过 `eax` 传回用户态**

---

```asm
ret_from_sys_call:
    popl %eax
    ...
    iret
```

* 主线解析 7：返回用户态

* 恢复之前保存的寄存器
* `iret`：

  * 恢复 CS / EIP / EFLAGS
  * **特权级从 0 → 3**
  * 回到用户程序

这是系统调用完整闭环的终点。

---

### 四 串连

形成一条完整路径：

```
用户程序
→ libc 中的 write()
→ int 0x80
→ CPU 查 IDT[0x80]
→ system_call
→ eax 校验
→ 保存现场
→ 切换内核段
→ sys_call_table[eax]()
→ 返回值放入 eax
→ iret
→ 回到用户程序
```

---

### 五 总结

要能清楚回答这 3 个问题就够了：

1. **eax 在 system_call 中起什么作用？**
   → 系统调用号 + 返回值

2. **`call sys_call_table(,%eax,4)` 在干什么？**
   → 按系统调用号查表并调用内核函数

3. **为什么最后用 `iret` 而不是 `ret`？**
   → 因为要返回用户态（涉及特权级切换）

## `_sys_call_table`：系统调用分发表


> **内核是如何根据系统调用号，准确调用到对应的系统调用函数的？**

---

### 一、`sys_call_table` 的本质

`sys_call_table` 是一个**全局函数指针数组**。

它的作用只有一个：

> **用“系统调用号”作为下标，找到对应的内核函数入口**

---

### 二、代码定义：函数指针数组

位置：`include/linux/sys.h`

```c
fn_ptr sys_call_table[] =
{
    sys_setup,
    sys_exit,
    sys_fork,
    sys_read,
    sys_write,
    ...
};
```

关键对应关系：

* `sys_write` 在数组中的下标是 **4**
* 而前面已经定义：

  ```c
  #define __NR_write 4
  ```

结论：

> **系统调用号 = sys_call_table 的数组下标**

这不是巧合，而是设计。

---

### 三、函数指针类型说明

位置：`include/linux/sched.h`

```c
typedef int (fn_ptr*)();
```

含义可以直接理解为：

* `fn_ptr`：指向“返回 int 的函数”的指针
* `sys_call_table`：`fn_ptr` 类型的数组

所以：

> `sys_call_table[i]` 本身就是一个“可被 call 的函数地址”

---

### 四、和汇编代码的精确对应关系（主线重点）

在 `system_call.s` 中的关键指令是：

```asm
call sys_call_table(,%eax,4)
```

这条指令的含义：

* `eax`：系统调用号
* 每个函数指针占 **4 字节**
* 实际跳转地址计算为：

  ```
  sys_call_table + 4 * eax
  ```

等价于 C 代码：

```c
sys_call_table[eax]();
```

当：

* `eax = 4`

实际效果就是：

```asm
call sys_write
```

---

### 五、把整个调用链完整串起来

到这里，**write 系统调用的整条链路已经闭环**：

```
用户程序调用 printf
    ↓
printf 内部调用 write（库函数）
    ↓
write 宏展开，执行 int 0x80
    ↓
CPU 进入内核态，跳转 system_call
    ↓
eax = __NR_write = 4
    ↓
call sys_call_table + 4 * eax
    ↓
调用 sys_write
```

---

### 反思


* `sys_call_table` 是什么？
  → **系统调用函数指针数组**

* 系统调用号和它是什么关系？
  → **系统调用号就是数组下标**

* `call sys_call_table(,%eax,4)` 本质在干嘛？
  → **根据系统调用号，调用对应的内核函数**

## `whoami` 系统调用的完整执行流程（总览）

这一节回答的是本章最核心的问题：

> **用户程序想“要点内核里的东西”，到底是怎么被允许、又是如何被限制的？**

---

### 一、用户态：只能“发请求”，不能“越权”

用户程序运行在 **用户态（CPL = 3）**，它的能力非常受限。

```c
main()
{
    whoami();
}

whoami()
{
    printf(100, 8);
}

/* 数据（逻辑上） */
100: "lizhijun"
```

这里要抓住两个关键点：

* 用户程序**不能直接 JMP 到内核代码**
* 也**不能随意访问内核中的数据地址**

即使“内存都是我买的”，**硬件也不允许你这么做**

所以这条路是被明确禁止的：

```
用户代码  ─X─>  直接跳到内核函数
```

---

### 二、用户态 → 内核态：唯一合法通道 `int 0x80`

既然不能乱跳，那用户程序**唯一能做的**是：

> **通过硬件规定的“入口”请求内核服务**

展开后的用户态代码本质是：

```c
main()
{
    eax = 72;     // 系统调用号：__NR_whoami = 72
    int 0x80;     // 触发中断，请求进入内核
}
```

这一步完成了三件事：

* 用户程序**主动请求**内核服务
* CPU **自动完成特权级切换**
* `CPL: 3 → 0`（用户态 → 内核态）

这是**唯一合法的越界方式**。

---

### 三、内核态：system_call 统一入口

`int 0x80` 触发后，CPU 跳转到内核中早已设置好的中断处理程序：

```asm
_system_call:
    call sys_call_table(,%eax,4)
```

此时的状态是：

* 已经在 **内核态（CPL = 0）**
* `eax = 72`
* 内核根据系统调用号 **查表**

也就是说：

```
sys_call_table[72]  →  sys_whoami
```

---

### 四、内核态：真正执行系统调用逻辑

被调用的内核函数是：

```c
sys_whoami()
{
    printk(100, 8);
}

/* 数据 */
100: "lizhijun"
```

注意这里的关键变化：

* 使用的是 **printk**（内核函数）
* 访问的是 **内核数据**
* 整个过程发生在 **CPL = 0**

这一步之所以安全，是因为：

> **代码和数据都在内核态，且由内核自己控制**

---

### 五、完整执行流（一条线记住）

```
用户程序 whoami()
    ↓   （CPL=3）
int 0x80（唯一合法入口）
    ↓   （硬件切换到 CPL=0）
system_call
    ↓
sys_call_table[eax]
    ↓
sys_whoami()
    ↓
printk 内核数据
```

---

### 六、本章的最终结论（一定要记住）

这一整章，其实只想牢牢记住一句话：

> **操作系统接口 = 系统调用
> 系统调用 = 用户态通过硬件机制，请求内核态代为执行受保护操作**

`whoami` 只是一个例子，但它把三件事一次性讲清楚了：

* 为什么用户程序不能“为所欲为”
* 为什么一定要有用户态 / 内核态
* 为什么系统调用必须走 `int` / 中断这条路
